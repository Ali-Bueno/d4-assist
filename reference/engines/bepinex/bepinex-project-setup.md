# BepInEx project setup — csproj, build loop, deploy

The runtime decides everything else. Pick the row, and the rest of the project follows.

| | Unity **Mono** | Unity **IL2CPP** |
|---|---|---|
| Package | `BepInEx.Unity.Mono` `6.0.0-be.*` | `BepInEx.Unity.IL2CPP` `6.0.0-be.*` |
| `TargetFramework` | `net472` | `net6.0` |
| Plugin base | `BaseUnityPlugin` — `Awake()` / `OnDestroy()` | `BasePlugin` — `Load()` / `Unload()`, **no MonoBehaviour lifecycle on the plugin itself** |
| Game references | `<Game>_Data\Managed\*.dll` | `BepInEx\interop\*.dll` |
| Custom MonoBehaviours | plain classes | must `ClassInjector.RegisterTypeInIl2Cpp<T>()` first |

Shipped examples: Core Keeper Access (Mono, net472), Megabonk Access (IL2CPP, Unity 2023.2.22f1,
net6.0), DRG Survivor Access (IL2CPP, Unity 6000.4.7f1, net6.0).

## 1. The csproj skeleton (IL2CPP)

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net6.0</TargetFramework>
    <LangVersion>latest</LangVersion>
    <AllowUnsafeBlocks>true</AllowUnsafeBlocks>
    <CopyLocalLockFileAssemblies>true</CopyLocalLockFileAssemblies>
    <RestoreAdditionalProjectSources>
      https://api.nuget.org/v3/index.json;
      https://nuget.bepinex.dev/v3/index.json;
      https://nuget.samboy.dev/v3/index.json
    </RestoreAdditionalProjectSources>
  </PropertyGroup>

  <PropertyGroup>
    <GameDir>D:\games\steam\steamapps\common\<Game></GameDir>
    <BepInExDir>$(GameDir)\BepInEx</BepInExDir>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="BepInEx.Unity.IL2CPP" Version="6.0.0-be.*" IncludeAssets="compile" />
    <PackageReference Include="BepInEx.PluginInfoProps" Version="2.*" />
    <!-- third-party libs you actually ship: -->
    <PackageReference Include="NAudio" Version="2.2.1" PrivateAssets="none" />
  </ItemGroup>

  <ItemGroup>
    <Reference Include="Assembly-CSharp">
      <HintPath>$(BepInExDir)\interop\Assembly-CSharp.dll</HintPath>
      <Private>false</Private>
    </Reference>
    <!-- …one per interop assembly you touch: UnityEngine, UnityEngine.CoreModule,
         UnityEngine.PhysicsModule, Unity.InputSystem, Unity.TextMeshPro,
         Il2Cppmscorlib, the game's own extra assemblies… -->
  </ItemGroup>
</Project>
```

Non-obvious bits:

- **The BepInEx package feed is `nuget.bepinex.dev`.** Bleeding-edge packages aren't on nuget.org.
  Keep all three feeds; `samboy.dev` carries related Unity/modding packages.
- **`IncludeAssets="compile"`** — reference BepInEx for compilation only, never copy it into `plugins/`
  (you'd load a second copy of BepInEx).
- **`<Private>false</Private>` on every game reference.** Copying `Assembly-CSharp.dll` into the plugins
  folder duplicates the game's types and breaks loading.
- **Do not add a Harmony `PackageReference`.** BepInEx already references it; a second copy causes
  version conflicts.
- **Do not touch the BepInEx package references** once a project builds — the exact combination is
  load-bearing.
- **`6.0.0-be.*` floats.** It is convenient and it silently changes what you build against. If a build
  matters (e.g. the Unity 6 / be.785 combination), pin the exact version and write it in the repo's
  README, because `core/` on disk is what actually runs.

### Where to point game references

Two working conventions, pick one per project:

- **Straight at the install** (`$(BepInExDir)\interop\…`, DRG) — always current after a regeneration,
  and the build breaks immediately when the game updates. Ties the repo to one machine's path.
- **Copied into `references/`** (Megabonk) — repo builds anywhere, but you must re-copy after every
  game update or you're compiling against stale signatures.

For Mono the same choice applies against `<Game>_Data\Managed\`.

### Colliding type names between game assemblies

Two game DLLs exporting the same namespace/type break the build. Alias one:

```xml
<Reference Include="Pug.Other">
  <HintPath>…\Pug.Other.dll</HintPath>
  <Aliases>PugOther,Game</Aliases>
  <Private>false</Private>
</Reference>
```

```csharp
extern alias PugOther;   // first line of the file that needs it
```

## 2. Plugin entry point

```csharp
// IL2CPP
[BepInPlugin(MyPluginInfo.PLUGIN_GUID, MyPluginInfo.PLUGIN_NAME, MyPluginInfo.PLUGIN_VERSION)]
public class Plugin : BasePlugin
{
    public static ManualLogSource Log;          // static so patch classes elsewhere can log
    private Harmony _harmony;

    public override void Load()
    {
        Log = base.Log;
        _harmony = new Harmony(MyPluginInfo.PLUGIN_GUID);
        _harmony.PatchAll();
        ClassInjector.RegisterTypeInIl2Cpp<MyComponent>();   // before any AddComponent<MyComponent>()
    }

    public override bool Unload()
    {
        _harmony.UnpatchSelf();
        return true;
    }
}
```

- `MyPluginInfo` is generated by **`BepInEx.PluginInfoProps`** from the csproj's `AssemblyName`,
  `Product` and `Version` — never hardcode GUID strings, and bump the mod version in the csproj only.
- The static `ManualLogSource` is the standard way patch classes log without an instance.
- On Mono the equivalent is `BaseUnityPlugin` with `Awake()`/`OnDestroy()`, and the plugin *is* a
  MonoBehaviour, so it can run coroutines itself. A `BasePlugin` cannot — put per-frame work in an
  injected MonoBehaviour you `AddComponent` onto a `DontDestroyOnLoad` object.
- Clean up symmetrically in `Unload()` (unpatch **and** shut down speech/audio). Asymmetric teardown is
  a common latent bug.

## 3. Build loop: `dotnet build` must deploy

The whole test loop is `dotnet build` → launch the game. Wire the copy into the csproj; never copy by
hand.

```xml
<Target Name="CopyToPlugins" AfterTargets="Build">
  <ItemGroup><FilesToCopy Include="$(TargetDir)*.dll" /></ItemGroup>
  <Copy SourceFiles="@(FilesToCopy)" DestinationFolder="$(BepInExDir)\plugins\<ModName>" />
</Target>

<!-- data files the mod loads at runtime -->
<Target Name="CopyAssets" AfterTargets="Build">
  <ItemGroup>
    <SoundFiles Include="sounds\**\*.*" />
    <LangFiles Include="localization\*.txt" />
  </ItemGroup>
  <Copy SourceFiles="@(SoundFiles)" DestinationFiles="@(SoundFiles->'$(BepInExDir)\plugins\<ModName>\%(Identity)')" />
  <Copy SourceFiles="@(LangFiles)"  DestinationFiles="@(LangFiles->'$(BepInExDir)\plugins\<ModName>\%(Identity)')" />
</Target>
```

Prefer MSBuild `<Copy>` over `<Exec Command="copy /Y …">`: it handles paths with spaces and reports
failures properly. Give the mod its **own subfolder** in `plugins/` so its data files and native DLLs
don't collide with other mods'.

Native DLLs are the exception — see §4.

## 4. What goes where at runtime

| File | Destination | Why |
|---|---|---|
| `<Mod>.dll` + managed deps (NAudio…) | `BepInEx\plugins\<Mod>\` | loaded by the chainloader |
| Data files (sounds, `localization/*.txt`, configs) | `BepInEx\plugins\<Mod>\` | resolve paths relative to the plugin assembly location, never to the CWD |
| `prism.dll` (PRISM) | next to the mod DLL, or game root | native lib, `LoadLibrary`/P-Invoke search path |
| `Tolk.dll` + `nvdaControllerClient64.dll` (legacy) | **game root** | Tolk's own loader looks there |
| `TolkDotNet.dll` (legacy managed wrapper) | `BepInEx\plugins\<Mod>\` | managed assembly |

Speech-library details and the PRISM-vs-Tolk decision live in
[accessibility-patterns.md](accessibility-patterns.md) and
[screen-reader-integration](../../screen-reader-integration/README.md).

## 5. Analyzer noise

`BepInEx.Analyzers` (Mono projects) emits **Harmony003** when a patch touches members of a struct
parameter. Fix by copying the parameter into a local first. Genuine false positives get a
`#pragma warning disable` **with a comment explaining why** — never a blanket suppression.
